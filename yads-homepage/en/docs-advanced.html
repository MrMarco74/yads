17. Best Practices

To get the most out of YADS, consider these tips:

💡 Pro Tip: Schedule regular scans during off-peak hours to minimize network impact.

  1. Tagging: Use tags creatively (e.g., prod, dev, critical) to organize targets.
  2. Regular Reviews: Check the Analytics page weekly to spot trends in vulnerability counts.
  3. Scope Definition: Be careful when adding root domains (e.g., company.com) as the Subdomain Recon module might find hundreds of assets.

Recommended Scanning Workflow

The following sequence has proven effective for comprehensive security assessments. Each phase builds upon the previous one, ensuring thorough coverage while maintaining efficiency.

Phase 1: Build Your Baseline

Start by establishing a foundation of known assets:

  • DNS Records (Simple) - Discover basic DNS information
  • Subdomain Recon - Enumerate all subdomains via Certificate Transparency logs

Phase 2: Identify Live Hosts

Determine which discovered assets are actively serving web content:

  • Quick Web Probe (80/443) - Check for web servers on standard ports

Phase 3: Deep Analysis of Online Assets

For all targets with status "online", run comprehensive analysis:

  • Web Analyzer - Technology stack detection
  • CVE Scanner (Passive) - Known vulnerability matching
  • Infrastructure - Server and hosting analysis
  • SSL Scanner - Certificate and encryption analysis
  • Visual OSINT - Screenshot capture and visual analysis
  • Wayback Machine - Historical data from web archives
  • Form Discovery (Passive) - Identify input forms and endpoints
  • Site Crawler - Map the site structure
  • Content Discovery (Fuzzing) - Find hidden paths and files

Phase 4: Expand Your Scope

Discover additional domains that may belong to the organization:

  • Typosquatting - Find lookalike domains (potential phishing)
  • TLD Scanner - Check for the domain across all TLD variants

Phase 5: Follow the Links

Review reports to identify additional targets worth investigating:

  • External Links - Discover linked external domains
  • Dead Links - Find broken links that may indicate abandoned assets

💡 Tip: If you discover new relevant domains in this phase, add them as targets and repeat from Phase 1 for those specific domains.

Phase 6: Active Vulnerability Testing

Once passive reconnaissance is complete, proceed with active scanning:

  • Nuclei Vulnerability Scan (Active) - Comprehensive vulnerability detection
  • Stealth Nmap Scan (Slow) - Port scanning with rate limiting

⚠️ Note: Active scans generate more traffic and may trigger security alerts. Ensure you have proper authorization before running these modules.

Phase 7: Housekeeping

Finally, clean up your target list:

  • DNS Health Check (Cleanup) - Identify and archive unreachable domains

18. Troubleshooting

Common Issues

🛑 Scan stuck in "Pending"

  • Cause: The background worker might be paused or overloaded.
  • Fix: Check Settings > Queue Control and ensure the queue is active. Check active workers count. The worker auto-heals every 60 seconds if it was paused.

⚠️ "Web Analyzer" failed

  • Cause: Target might be offline or blocking the scanner.
  • Fix: Try visiting the URL manually. Adjust Web Request Timeout in settings if the site is slow.

🚫 MFA Code Rejected

  • Cause: Time drift on the server or client.
  • Fix: Ensure your server time is synced via NTP.

20. Standalone & Local Installation

Prerequisites

  • Docker ≥ 24
  • Docker Compose Plugin ≥ 2.20
  • 4 GB RAM (recommended: 8 GB)
  • 20 GB free disk space

Minimal Installation (Core only)

Starts the API, worker, database, and Redis without optional services:

docker compose up -d

With Identity Provider

docker compose --profile keycloak up -d

With Monitoring Stack

docker compose --profile monitoring up -d

Full Installation

docker compose --profile keycloak --profile monitoring up -d

Alternatively, set the profiles in your .env file:

COMPOSE_PROFILES=keycloak,monitoring

First Launch

  1. After startup, open the Setup Wizard at http://localhost:8085/setup.
  2. Create the admin account and enter your license key.
  3. Configuration is stored in data/config.env and managed via the UI.

Configuration

  • Template: .env.example — complete reference template with all available variables
  • Persistent runtime configuration: data/config.env (saved via the UI)

Integrating External Services

If Keycloak or Prometheus are already running externally, only set the corresponding environment variables — no additional container needed:

AUTH_MODE=oidc
OIDC_SERVER_URL=http://your-keycloak:8080
OIDC_PUBLIC_URL=https://keycloak.your-domain.com

User Migration to Keycloak

python scripts/maintenance/migrate_users_to_keycloak.py \
  --keycloak-url http://keycloak:8080 \
  --dry-run

Note: Kubernetes and cloud deployment will be documented in a separate chapter (coming soon).

21. Identity Provider & SSO

Authentication Modes

  • AUTH_MODE=local (default): Local user management, no external dependency.
  • AUTH_MODE=oidc: Keycloak or any OIDC-compliant identity provider.

URL Configuration for Docker Deployments

  • OIDC_SERVER_URL: Internal URL for server-to-server communication (e.g., http://keycloak:8080)
  • OIDC_PUBLIC_URL: Public URL for browser redirects (e.g., https://keycloak.your-domain.com)

Realm Concept

A dedicated Keycloak realm per YADS tenant is recommended to ensure complete tenant isolation at the identity provider level.

Group Mapping

Keycloak GroupYADS Role
{tenant}-adminstenant_admin
{tenant}-scannersscanner
{tenant}-auditorsauditor
yads-platform-adminsadmin

Keycloak Client Configuration

The following Protocol Mappers must be configured in the Keycloak client:

  • groups: Transmits group memberships as a JWT claim
  • yads_tenant (hardcoded): Specifies the tenant identifier

Migrating Existing Users

python scripts/maintenance/migrate_users_to_keycloak.py \
  --keycloak-url http://keycloak:8080 \
  --realm yads \
  --dry-run

Remove --dry-run to execute the migration. Existing local passwords are preserved as a fallback as long as AUTH_MODE=local is active.

22. Developer Portal

The Developer Portal (/developer) provides everything needed to integrate YADS into CI/CD pipelines, SIEM systems, or custom tooling.

API Key Management

  • Generate API keys with optional expiry dates (30d, 90d, 1y, or no expiry)
  • Keys are shown only once on creation — copy and store securely
  • Revoke keys at any time; revoked keys are rejected immediately

Authentication

Pass the API key in the X-API-Key header:

curl -H "X-API-Key: yads_your_key_here" https://your-yads-instance/api/targets

Code Examples

The portal includes ready-to-use snippets for curl, Python (requests), and JavaScript (fetch) covering authentication, target listing, scan triggering, and result retrieval.

Rate Limits

Most API endpoints600 req/min
Scan trigger60 req/min
Report generation10 req/min

24. Onboarding Wizard

New tenants are guided through a 4-step wizard on first login:

  1. Welcome — Overview of YADS capabilities and key features
  2. Add Target — Enter the first domain to monitor
  3. First Scan — Select a scan profile and launch the initial assessment
  4. Done — Links to the dashboard, targets list, and documentation

The wizard can be dismissed at any time via the "Skip wizard" link. Once dismissed (or completed), it does not reappear. Platform admins can re-trigger it for a tenant by removing the ONBOARDING_DONE_{tenant_id} key in System Settings → Configuration.

25. Data Retention

YADS can automatically prune old scan results to keep the database size manageable in long-running deployments.

Configuration

Go to Settings → Data Retention and set the retention period in days (default: 90). Setting it to 0 disables pruning (keep forever).

Pruning Behavior

  • A Celery beat task runs daily at midnight UTC
  • Deletes ChangeEvent rows older than the retention window first, then ScanResult rows
  • The latest scan result per module per target is never pruned (protected)
  • Affected rows are logged to the system log

26. Excel Export

Every target detail page has an Excel Export button that generates a multi-sheet XLSX file covering all 20+ scanner modules.

Sheets Included

  • Summary — Target metadata, security score, scan timestamps
  • DNS Records, Subdomains, SSL/TLS, HTTP Headers, Cookies, CORS
  • Email Security (SPF/DKIM/DMARC), Threat Intelligence, Shodan/Censys
  • Nuclei Findings, Web Technologies, External Links, Security Findings

Language Support

Append ?lang=de to the export URL for German column headers and labels. The default is English (?lang=en).

27. Attack Path Visualizer

The Attack Path Visualizer (Intelligence → Attack Paths) generates a directed graph that links exposed services, misconfigurations, and known vulnerabilities into plausible multi-step attack chains.

How it Works

  • Aggregates findings from all scanner modules for a target.
  • Applies a ruleset to connect nodes: e.g., "Open port 22 + weak SSH banner → Brute-force entry point → Internal pivot".
  • Renders an interactive D3.js graph with severity-coloured nodes (red = critical, orange = high, yellow = medium).

Using the Visualizer

  1. Open a target detail page and click Attack Paths in the top action bar.
  2. The graph loads automatically. Hover a node to see the finding detail. Click to pin and inspect the edge labels.
  3. Use the Export SVG button to embed the graph in reports or presentations.

Risk Score Integration

Chains with 3+ hops and a critical entry node add a -10 penalty to the overall security score, surfaced as the "Multi-hop attack path detected" factor.

28. Scan Comparison

Scan Comparison lets you diff two historical scan results for the same target to pinpoint exactly what changed between runs.

Accessing Comparison

  1. Go to Target → Change History.
  2. Select two scan result entries (checkboxes) and click Compare.
  3. A side-by-side diff view highlights added/removed/changed fields per module.

What is Compared

  • All structured module data fields (DNS records, open ports, headers, TLS grade, score, etc.).
  • New findings present in the newer scan but absent in the older one are highlighted in green.
  • Resolved findings (present in old, absent in new) are highlighted in red with a strikethrough.

Export

Use Export Diff PDF to generate a comparison report suitable for customer delivery or compliance evidence.

29. WAF Analysis

The WAF Detector module probes whether a target is protected by a Web Application Firewall, identifies the vendor, and evaluates bypass exposure.

Detection Methods

  • HTTP response header fingerprinting (Server, X-Sucuri-ID, X-Powered-By, cf-ray, etc.).
  • Cookie name analysis (e.g., __cfduid, TS01..., incap_ses_).
  • Response-code behaviour under crafted payloads (SQLi, XSS probes).

Result Fields

  • WAF Detected: Boolean — yes/no.
  • Vendor: Detected product name (Cloudflare, Sucuri, Imperva, AWS WAF, F5 BIG-IP, Barracuda, …).
  • Confidence: Low / Medium / High — based on number of matching signals.
  • Bypass Risk: Whether generic bypass techniques may evade the detected WAF.

Score Impact

No WAF detected on a domain with externally reachable web services: -5 penalty. WAF detected at High confidence: +5 bonus.

30. Scanner Import

YADS can ingest external scan results from popular tools via the Scanner Import feature (Settings → Scanner Import), eliminating double scanning and enabling a single pane of glass.

Supported Formats

  • Nmap XML (-oX) — port states, service versions, OS guesses.
  • Nuclei JSONL — template IDs, severity, matched-at URLs.
  • Burp Suite XML — issue list with severity and confidence.
  • OWASP ZAP JSON — alert list.
  • Generic CSV — configurable column mapping.

Import Process

  1. Navigate to Settings → Scanner Import.
  2. Select the target from the dropdown.
  3. Choose the file format and upload the result file.
  4. YADS normalises findings into the standard ScanResult schema and creates ChangeEvent records for any new findings.
  5. Imported results appear in the target's Finding Overview and are included in score calculation.

31. Integrations (Jira / GitHub / SIEM / Webhook)

YADS provides first-class integrations with issue trackers, code repositories, and SIEM platforms via a unified webhook and API system.

Webhook System

Configure webhooks at Settings → Webhooks. Each webhook fires on one or more events:

  • scan_finished — after every scan run (payload includes score delta).
  • finding_new — when a new finding is detected (severity filter available).
  • finding_resolved — when a previously open finding disappears.
  • score_drop — when the security score falls by ≥ 10 points.
  • target_archived — when a dead domain is archived.

Jira Integration

  • Configure the Jira base URL, project key, and API token in Settings → Integrations → Jira.
  • New critical/high findings automatically create Jira issues with pre-filled summary, description, and severity label.
  • Issue state is synced: when YADS marks a finding resolved, the Jira issue moves to "Done".

GitHub Integration

  • Connect a GitHub repository via personal access token in Settings → Integrations → GitHub.
  • New findings open GitHub Issues with appropriate labels (security, high, etc.).
  • Supports both github.com and GitHub Enterprise Server.

SIEM / Splunk

  • Configure Splunk HTTP Event Collector (HEC) URL and token in Settings → Integrations → Splunk.
  • Every scan result and finding event is forwarded as structured JSON to the configured HEC endpoint.
  • Generic syslog forwarding is also available for other SIEM platforms.

Slack / Microsoft Teams

  • Enter an Incoming Webhook URL in Settings → Notifications.
  • Select event types and a minimum severity threshold.
  • Notifications are sent as rich card messages with score, finding count, and a direct link to the target.
